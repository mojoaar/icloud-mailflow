Introduction

Apple's iCloud Mail rules are basically useless — a single condition, a single action, and no way to chain anything. Combined with a web client they haven't meaningfully updated in years, managing iCloud mail beyond the basics is a dead end.

Mailflow fixes that. It connects to iCloud via IMAP, runs your incoming mail through a real rules engine (AND/OR logic, 13 condition operators, multiple actions), and handles it all automatically.

Getting Started

1. iCloud Mail Rule

Create a rule on iCloud to route all incoming mail to the Processing folder:

  1. Go to icloud.com/mail
  2. Settings gear → Rules → Add a Rule
  3. If a message → is addressed to → leave address empty
  4. Then → Move to Folder → New Folder… → enter Processing
  5. Click Done twice

2. App-Specific Password

Generate at appleid.apple.com → Sign-In & Security → App-Specific Passwords.

3. Start the App

go run ./cmd/mailflow/ -data=./data

Open http://{{.Host}}/setup → configure admin password + iCloud email + app password.

4. Docker

docker compose up -d
docker compose restart  # after setup → IMAP reconnects

How It Works

Incoming mail → iCloud Rule → "Processing" folder → Mailflow poller → Match rules → Execute actions
  1. iCloud rule moves all incoming mail to the Processing folder
  2. Mailflow polls Processing every 300s (configurable, default 50 messages/poll)
  3. Each message is checked against your rules in priority order (lowest first)
  4. First matching rule's actions execute — if none match, the catch-all handles it
  5. Contacts are auto-collected from message headers (From, To, Cc)

Rules & Conditions

Rules are checked in priority order — lowest number runs first. Reorder via drag & drop.

Operators

Text: equals · not_equals · contains · not_contains · starts_with · ends_with · matches_regex

Boolean: exists · not_exists

Date: older_than ("7 days") · newer_than ("30 days") · before (ISO date) · after (ISO date)

Match Logic

  • ANY (OR): Rule fires if any ONE condition is true — default for new rules
  • ALL (AND): Rule fires only if every condition matches

Scheduling

Each rule can be limited to specific days and times using schedule_days (comma-separated mon,tue,wed,thu,fri,sat,sun), schedule_start and schedule_end (HH:MM, in your configured timezone). Leave all blank to always run. A scheduled rule that doesn't match the current time is skipped — the message stays unseen and is re-checked on the next tick.

Nested Groups

Conditions can be nested into AND/OR groups — for example (from contains @a.com OR subject starts_with "Invoice") AND has_attachment. Each group has its own ALL/ANY operator; use + Group to nest and Remove group to delete. Nested groups round-trip through export, backup, and MCP.

Regex Capture

A matches_regex condition with named capture groups (e.g. (?P<order>\d+)) exposes each group as [capture:order] in auto_reply templates; the full match is available as [capture:0].

Test & Apply

Use Test Rule on the rule edit form to check a rule against synthetic fields or a real IMAP message with a per-condition pass/fail breakdown. Use Apply to Folder on the Rules page to retroactively run all enabled rules over an existing folder.

Actions execute strictly in declared order. For iCloud, place mark_as_read before move_to_folder — iCloud requires \Seen before allowing MOVE.

auto_reply is throttled to at most one reply per sender per day, and replies to the account's own address are skipped to prevent mail loops.

Contacts

Mailflow automatically collects sender and recipient addresses from processed messages. Automatic collection can be disabled, and contacts can be wiped from Settings or MCP.

  • Automatic Collection — Emails from, to, and cc addresses are collected during each poll tick (can be disabled via Settings)
  • Seed Contacts — Bulk import across all IMAP folders (newest 200 each)
  • iCloud Contacts — Import address book via CardDAV (Settings)
  • Wipe Contacts — Delete all collected contacts from Settings or MCP
  • Autocomplete — Contacts suggest in rule condition value inputs
  • Count — Shown on Dashboard and Settings → Server

Activity Log

Every rule match and action execution is logged. View at /activity.

  • Shows timestamp, subject, sender, rule, action, and status
  • Timezone-adjustable in Settings → Regional
  • Run rules on any row re-evaluates the current rules against that message (dry-run, no actions)
  • Clear logs with "Clear Logs" button
  • Auto-cleaned on startup (default 1000 entries, configurable in Settings)

Stats Dashboard

Visit /stats for rule hit counts, top senders, actions breakdown, daily/weekly volume, messages by folder, and runtime metrics charts (Memory and CPU %). A range selector (7/30/90 days) scopes the daily and weekly volume, and a Poller card shows the last run time, duration, health, and consecutive failures. Charts are interactive (Chart.js) with a per-section List/Chart toggle, and they recolor live when the theme changes. Daily/weekly buckets and chart time axes follow the configured timezone. Status totals (success/error/skipped) are shown under the all-time processed count. Stats are stored independently from the activity log — clearing logs preserves all statistics.

The range is also addressable directly: /stats?days=7, /stats?days=30, or /stats?days=90.

Themes & Appearance

Mailflow ships nine colour themes, each with a dark and light variant: Mailflow (default), Ayu, Catppuccin, Cyberpunk, Dracula, Gruvbox, Nord, One Dark, and Tokyo Night.

  • Choose a family in Settings → Regional → Theme; switch between dark and light with the moon/sun icon in the header
  • On your first visit the theme follows your operating system's light/dark preference
  • Syntax highlighting on this page and the charts on Stats follow the active theme, and charts recolor instantly when you switch
  • The choice is stored per browser (localStorage) and is not saved on the server — set it on each device

MCP Server

Mailflow exposes a Model Context Protocol (MCP) server so AI agents (Claude Code, OpenCode, Codex) can manage rules, check stats, and trigger polls remotely. Enable it in Settings → MCP Access — you get an API key and ready-to-use config snippets for all platforms.

The server runs over HTTP on /mcp. All 26 tools require a Bearer token in the Authorization header.

API Reference

Base URL: http://{{.Host}}. Most endpoints require a session cookie from POST /login. Public endpoints (/health, /metrics, /docs, /login, /setup, /static) do not.

Authentication

POST POST /login

Authenticate. Returns mailflow_session cookie. Rate limited: 5/min/IP.

curl -X POST http://{{.Host}}/login -d "password=YOUR_PASSWORD" -c cookies.txt

POST POST /logout

Clear session cookie and redirect to login. Requires CSRF token.

curl -X POST http://{{.Host}}/logout -b cookies.txt -d "csrf_token=$TOKEN"

GET GET /setup

First-run setup page. Configure admin password and iCloud IMAP credentials.

curl http://{{.Host}}/setup

POST POST /setup

Submit initial setup form (password, IMAP email, app-specific password).

curl -X POST http://{{.Host}}/setup \
  -d "password=admin123&imap_email=user@icloud.com&imap_password=app-password"

Polling

Trigger a manual poll cycle immediately.

curl -X POST http://{{.Host}}/poller/tick -b cookies.txt

POST POST /settings/poll/toggle

Enable or disable automatic polling.

curl -X POST http://{{.Host}}/settings/poll/toggle -b cookies.txt

GET GET /dashboard/status

Live poller status HTML fragment (auto-refreshed by dashboard every 30s). Returns running state, health, last tick, last duration, and processing status.

curl http://{{.Host}}/dashboard/status -b cookies.txt

GET GET /dashboard/rules

Rules table HTML fragment (auto-refreshed by dashboard every 60s). Returns each rule's name, conditions summary, and enabled status with Edit buttons.

curl http://{{.Host}}/dashboard/rules -b cookies.txt

Rules

POST POST /rules

Create a new rule. Conditions and actions parsed from form data.

curl -X POST http://{{.Host}}/rules -b cookies.txt \
  -d "name=My+Rule&enabled=on&cond_field=from&cond_op=contains&cond_value=@work.com&cond_operator=OR&action_type=move_to_folder&action_value=Work"

PUT PUT /rules/{id}

Update an existing rule. Use _method=PUT in form data.

curl -X POST http://{{.Host}}/rules/1 -b cookies.txt \
  -d "_method=PUT&name=Updated+Rule&enabled=on"

DEL DELETE /rules/{id}

Delete a rule by ID. Use _method=DELETE in form data.

curl -X POST http://{{.Host}}/rules/1 -b cookies.txt -d "_method=DELETE"

POST POST /rules/reorder

Reorder rules by priority. Submit rule_ids in the desired order.

curl -X POST http://{{.Host}}/rules/reorder -b cookies.txt \
  -d "rule_ids=3&rule_ids=1&rule_ids=2"

POST POST /rules/reorder/move

Move a rule up or down by one position for keyboard-accessible reordering. Submit rule_id and direction (up or down).

curl -X POST http://{{.Host}}/rules/reorder/move -b cookies.txt \
  -d "rule_id=3&direction=up"

POST POST /rules/{id}/test

Dry-run rule against synthetic message fields (from, to, cc, subject). Returns per-condition pass/fail with actual vs expected values.

FieldTypeRequiredDescription
fromstringNoSender email
tostringNoRecipient email
ccstringNoCC email
subjectstringNoEmail subject
curl -X POST http://{{.Host}}/rules/1/test -b cookies.txt \
  -d "from=user@test.com&subject=Hello&to=recipient@test.com&cc=cc@test.com"

POST POST /rules/{id}/test-message

Dry-run rule against a real message fetched from IMAP in the given folder. Fetches body and headers for full evaluation.

GET GET /settings/rules/export

Download all rules as JSON (excludes catch-all). Includes priority, enabled state, and schedules.

curl http://{{.Host}}/settings/rules/export -b cookies.txt -o rules.json

POST POST /settings/rules/import

Import rules from a JSON file — accepts the export/scheduled-backup format, with or without the {"rules":[...]} envelope.

curl -X POST http://{{.Host}}/settings/rules/import -b cookies.txt \
  -F "rules_file=@rules.json"

CSRF & HTMX

State-changing form posts require a csrf_token matching the mailflow_csrf cookie. HTMX-issued requests (HX-Request: true) are exempt from the CSRF token by design and are instead protected by the SameSite=Strict session cookie, which prevents cross-site requests from carrying credentials.
